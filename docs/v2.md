# Daily Calorie Tracker

React + TypeScript + Tailwind CSS로 마이그레이션한 **데일리 칼로리 트래커**입니다.

V1에서는 Vanilla JavaScript와 localStorage를 사용해 MVP 기능을 빠르게 구현했고, V2에서는 **React 기반 컴포넌트** 구조로 전환하고 **Supabase**를 연동하여 사용자별 음식 데이터를 관리할 수 있도록 개선했습니다.

음식 이름과 탄수화물, 단백질, 지방을 입력하면 음식 카드가 생성되고, 저장된 데이터를 기반으로 총 칼로리와 영양소 정보를 확인할 수 있습니다. 로그인 / 회원가입 / 비밀번호 재설정 기능을 추가해 사용자 인증 흐름을 구성했습니다.

---

# 소개

**React 기반 프론트엔드 구조로 마이그레이션한 V2 버전**입니다.

- Vanilla JS → React 컴포넌트 구조
- JavaScript → TypeScript
- CSS → Tailwind CSS
- localStorage → Supabase 기반 데이터 관리
- React Router 기반 페이지 라우팅 + 로그인 상태에 따른 접근 제어
- 사용자 인증 기능 (회원가입 / 로그인 / 로그아웃 / 비밀번호 재설정) 추가
- API 요청 로직과 UI 로직 분리 (services / hooks 구조)

V2에서 중심으로 구성된 기능은 다음과 같습니다.

- 사용자 인증 및 로그인 상태 기반 접근 제어
- 음식 데이터 추가 / 수정 / 삭제 (Supabase 연동)
- 날짜 기반 음식 기록 관리
- 입력 유효성 검사 (규칙 기반 구조로 확장)

# 주요 기능

**사용자 인증**
- 이메일 / 비밀번호 기반 회원가입, 로그인, 로그아웃
- 비밀번호 재설정 메일 발송 및 재설정 처리 (만료/잘못된 링크 에러 처리 포함)
- 로그인 상태에 따른 페이지 접근 제어 (비로그인 시 메인/월간 페이지 접근 차단, 로그인 시 로그인/회원가입 페이지 접근 차단)
- Supabase 에러를 사용자 친화적 메시지로 변환

**음식 데이터 관리**
- 음식 추가 (이름, 식사 유형, 탄수화물, 단백질, 지방, 기록 날짜)
- 음식 수정 / 삭제 (삭제 시 확인 알림)
- 날짜(`record_date`) 기준 기록 관리 → 일간/주간/월간 통계로 확장 가능한 구조
- 월간 기록 페이지 (날짜별 기록 조회, 추후 월별 통계로 확장 예정)

**입력 유효성 검사**
- 공통 검증 유틸을 규칙 기반(Validation Rule)으로 구성: `required`, `minLength`, `match`, `pattern`, `minNumber`
- 로그인/회원가입/음식 추가 및 수정 폼에서 재사용

# 프로젝트 구조

```bash
src/
├── components/          # 전역 공통 UI 컴포넌트
├── features/
│   ├── foods/            # 음식 데이터 CRUD (components / hooks / services / utils)
│   └── tracker/           # 데일리 / 위클리 / 먼슬리 트래커 UI
├── lib/
│   └── supabase.ts        # Supabase 클라이언트 설정
├── pages/
│   ├── daily-tracker/      # 하루 단위 음식 기록 페이지
│   ├── monthly-tracker/    # 월간 기록 페이지
│   └── user/               # 로그인 / 회원가입 / 비밀번호 재설정 페이지
├── service/
│   └── UserService.ts      # Supabase Auth 관련 인증 로직
├── store/                  # Zustand 전역 상태 (authStore, foodStore)
├── types/                  # 공통 TypeScript 타입
├── utils/                  # 공통 유틸 (calculate, date, sweetAlert, validateCommonInput)
├── App.tsx                 # 라우팅 및 로그인 상태 기반 접근 제어
└── main.tsx
```

컴포넌트에서 직접 API를 호출하지 않고 `hooks`와 `services`로 분리해, UI 로직과 데이터 요청 로직을 구분했습니다. 이 구조는 이후 Spring Boot REST API로 전환할 때 수정 범위를 줄이는 것을 목표로 합니다.

# 코드 구조 설명

## App.tsx

- 페이지 라우팅 설정
- 로그인 상태에 따른 접근 제어 및 리다이렉트 처리

## service/UserService.ts

- 회원가입 / 로그인 / 로그아웃
- 비밀번호 재설정 이메일 전송 및 새 비밀번호 변경

## store/authStore.ts, foodStore.ts

- Zustand 기반 전역 상태 관리
- 로그인 사용자 정보, 음식 및 기록 화면 공유 상태

## utils/validateCommonInput.ts

- 규칙 기반(Validation Rule) 입력 검증 유틸
- `required`, `minLength`, `match`, `pattern`, `minNumber` 지원
- 로그인 / 회원가입 / 음식 추가·수정 폼에서 공통 사용

# 데이터 구조 예시

```javascript
{
  id: 1,
  userId: "user-uuid",
  mealType: "breakfast",
  foodName: "Banana",
  carbs: 27,
  protein: 1,
  fat: 0,
  recordDate: "2026-06-21",
  createdAt: "2026-06-21T12:00:00"
}
```

V1의 `{ foodId, name, carbs, protein, fat }` 구조에서 `userId`(사용자별 구분)와 `recordDate`(날짜 기반 기록 관리)가 추가됐습니다.

# 회고

V1에서는 Vanilla JS로 MVP를 빠르게 구현하며 DOM 조작과 localStorage 기반 데이터 관리를 학습했지만, 기능이 늘어날수록 UI 상태와 저장 데이터의 일관성을 유지하기 어려웠습니다. 당시 storage 기준으로 전체를 재렌더링하는 구조로 바꾸면서 이 문제를 해결했었는데, 이 경험이 V2에서 React의 상태 기반 렌더링 방식을 받아들이는 데 자연스러운 발판이 됐습니다.

V2에서는 React + TypeScript + Supabase로 마이그레이션하면서 컴포넌트 단위 설계, 상태 기반 렌더링, 서비스 레이어 분리를 통해 유지보수하기 쉬운 구조를 고민했습니다. 이후 Spring Boot와 MyBatis 기반 백엔드를 직접 구축해 풀스택 구조로 확장할 예정입니다.
